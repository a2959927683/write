# 0001 · 主控定位: Orchestrator 而非产品本身

## 状态
已采纳 · 2026-06-07

## 背景
用户要求"项目主控的角色", 同时让"前端 / 后端 / AI 调度"等都作为子项目。
存在两种合理路径:
- **路径 A**: 主控直接做产品 (写前端 + 后端 + AI)
- **路径 B**: 主控只做契约 + 调度, 子项目实现

## 决策
**主控采用路径 B**: 主控 = 前后端契约权威 + 调度中枢, 不写产品 UI/UX 本身。

## 备选

### 备选 A: 主控直接做产品
- ✅ 简单直接, 一个人干完
- ❌ 容易陷入细节, 失去全局视角
- ❌ 后续团队接手时主控角色模糊
- ❌ 不利于前后端并行

### 备选 B (已采纳): 主控只做契约 + 调度
- ✅ 主控保持全局视角
- ✅ 前后端可以并行
- ✅ 子项目可以独立演进
- ❌ 需要清晰的契约, 否则子项目会脱节

## 理由
1. 用户明确说"主控 + 制定前后端契约 + 把握项目方向"
2. 主控的 4 大职责 (契约/方向/调度/一致性) 都需要全局视角
3. 主控如果下场写 UI, 容易成为瓶颈
4. 子项目通过契约 (OpenAPI + JSON Schema) 沟通, 互不阻塞

## 影响
- 主控根目录包含 `backend/`, `frontend/`, `ai-orchestrator/`, `knowledge-graph/`, `infra/` 5 个**空目录骨架**
- 主控产出物只有 `contracts/`, `docs/`, `feature_list.json`, `progress.txt`, ADR
- 任何写产品代码的需求, 主控**派发给子项目** (用 `dispatching-parallel-agents` 或拆 `feature_list.json`)

## 后续
- 第一次有真实子项目实现需求时, 先在 `feature_list.json` 加任务
- 子项目由独立的 Claude Code 会话 (或 `using-git-worktrees` worktree) 实现
- 主控监督进度, 解决跨子项目冲突
