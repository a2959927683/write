📋 Q1 · brief 模板

brief 字段够不够?要不要加?

原 6 字段: 任务 / 必读契约 / 技术约束 / 验收 / 不要做 / 想深挖再看

教练推荐:升级到 9 字段(加 3 个)

新增 3 个字段:

  • 📌 依赖任务 · 告诉 agent "等 S0-15 完才能开工"
  • ⏱️ 估算工时 · 1h / 4h / 1day,主控判超时
  • 🚨 失败回滚 · 失败时怎么撤销,不留垃圾

升级版 brief 模板(9 字段):

# S0-18 · auth 模块实现 brief ━━━━━━━━━━ 必填 (9 字段) ━━━━━━━━━━ ## 🎯 任务 [必填] 实现 8 个认证端点 + JWT + 30s 心跳 ## 📌 依赖任务 [新增 · 必填] - 必须先完成: S0-15 (Docker), S0-17 (Prisma schema) - 完工后阻塞: S0-23 (前端登录页) ## 📜 必读契约 [必填] - contracts/openapi/auth.yaml - contracts/schemas/user.json ## 🔧 技术约束 [必填] - JWT HS256, 7 天有效期 - bcrypt 密码哈希 - 中文字段名: 最高角色等级 ## ⏱️ 估算工时 [新增 · 必填] 4 小时 (超 6h 必须报警) ## ✅ 验收 [必填] curl http://localhost:3000/api/auth/login → { success, token, user } ## 🚫 不要做 [必填] - 不实现注册短信发送 (留 stub) - 不碰其他模块 ## 🚨 失败回滚 [新增 · 必填] git reset --hard origin/main; prisma migrate reset ## 📚 想深挖再看 [可选] - knowlage/wiki/sources/API认证与架构.md
为什么加这 3 个:

· 依赖任务:防止 agent 抢跑(后端没好就写前端联调)

· 估算工时:主控判超时(4h 任务卡 8h = 出问题了)

· 失败回滚:防止失败 agent 留下脏数据/脏代码

🐛 Q3 · brief 写错怎么办

子 agent 发现 brief 错了,能反向修正吗?

教练推荐:子 agent 只能反馈,主控决定改不改 + 必须留痕

4 步反馈流程:

1 子 agent 发现 brief 错

例:brief 说"用 HS256",但契约里写"RS256"

2 子 agent 立刻停手,写反馈

在 backend/progress.txt 写 🚨 BRIEF_ERROR 标记

3 主控来仲裁

主控对比 brief vs 契约,判谁错

4 主控改 brief,子 agent 继续

主控更新 brief + commit + 通知 agent 重启

3 条铁律:

· ❌ 子 agent 绝对不能自己改 brief(否则失去权威)

· ✅ 必须留痕(progress.txt 里记 BRIEF_ERROR,可追溯)

· ⏱️ 主控 30 分钟内响应(否则子 agent 转去做别的任务)

🔁 Q4 · 调试回流

L3-v4-Lite 的"调试"阶段如何回流主控?

选项评价
A. 写在 progress.txt(主控自己看)✅ 简单,但易遗漏
B. 发 issue 到 master/issues/✅ 结构化,可追溯
👑C. A + B 混合 + 标签分级🏆 主控不漏问题
D. 触发主控 agent 来仲裁❌ 过重,延迟高
教练推荐:C · 双轨制 + 3 级标签

🟢 小问题

→ 写 progress.txt
用 [INFO] 标签
主控定期看

→

🟡 中问题

→ 写 issues/
用 [WARN] 标签
主控 1 天内回

🔴 大问题(契约错/阻塞)

→ progress + issues 都写
用 [CRITICAL] 标签
主控 30 分钟内回

→

📡 紧急广播

→ 触发主控通知
SendMessage 推送
主控立刻响应

3 级标签的好处:

· 小问题不打扰主控 → 效率

· 大问题不会被埋 → 兜底

· 紧急广播立即响应 → 不阻塞主链

📚 Q5 · INDEX 维护

knowlage/INDEX.md 谁维护?谁判断"权威"?

教练推荐:主控独家维护,子 agent 只能"建议",不能"修改"

✅ 主控可以做

  • 新增条目到 INDEX.md
  • 修订条目的"权威"标记
  • 下线过期的 source
  • 合并冲突的 source
  • 判定哪条是 authoritative

❌ 子 agent 不能做

  • 修改 INDEX.md
  • 判定权威性
  • 新增条目
  • 修改 source 文件
  • 但可以 → 给主控提建议

子 agent 提建议的格式:

# backend/progress.txt 里追加 [INDEX_SUGGEST] 2026-06-08 14:30 建议: 在 knowlage/INDEX.md 新增条目 - 路径: wiki/sources/2026-06-08 新发现的 X.md - 主题: Y 模块的某细节 - 优先级: 高 理由: 写 S0-18 时发现该资料未被索引
为什么主控独占:

· 权威性来源唯一(否则各 agent 自说自话)

· 避免循环引用(A 改 INDEX 影响 B 的判断)

· 主控负责裁决冲突(C01-C11 11 条冲突就是主控决的)

🤖 Q6 · 二级 agent

二级 research-agent 用 isolation 还是直接 spawn?

方案 A · isolation worktree

起独立 git worktree, 完全隔离

✅ 完全隔离, 不污染父 context
✅ 可并行多个 research
❌ 200-500ms 启动开销
❌ 占磁盘空间

方案 B · 直接 spawn(Task 工具)

在父 agent 内调 Agent 工具, 共享 context

✅ 零开销, 立即启动
✅ 简单, 不用管 git
❌ research 失败会污染父 agent
❌ 不能并行多个
教练推荐:按场景选 · 默认 B,需并行才用 A

决策规则:

  • 🎯 research-agent 短命 (<5min) → 直接 spawn (B)
  • 🎯 研究多个独立主题 → isolation (A) 并行
  • 🎯 需要写文件 → 必须 isolation (A) 防污染
  • 🎯 只读 + 总结 + 退场 → 直接 spawn (B) 最轻
实战 90% 用 B:

· research-agent 的核心是"读 + 总结",不写文件

· 读完 5 行总结返回 → 父 agent context 几乎不增

· 启动开销 0,响应快

· 只有遇到"3 个 research 主题并行"才上 isolation
