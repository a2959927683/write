⚙️ Q1 · 分支策略

每个子 agent 怎么开分支?

选项谁在用优缺
A. 一 agent 一分支(backend-dev)中小团队简单任务多了乱
B. 一任务一分支(feature/S0-18)大厂 GitHub Flow清晰分支爆炸
👑C. 主线+worktreeAI 时代新玩法快依赖 worktree
教练推荐:B + C 混合
main (主控守护, 永远稳定) ├─ feature/S0-18-auth ← backend agent 在 worktree-1 干 ├─ feature/S0-22-vue-shell ← frontend agent 在 worktree-2 干 └─ feature/S0-15-docker ← infra agent 在 worktree-3 干
为什么:

· 一任务一分支 → 完工合一个,失败回滚一个,互不连坐

· worktree 隔离 → 物理目录分开,不会改到对方文件

· AI agent 适合"短命分支"(几小时完工就合)

📝 Q2 · commit 规范

commit 消息写什么风格?

选项谁在用评价
A. Conventional 英文开源项目主流✅ 通用
B. Conventional 中文国内大厂✅ 团队中文友好
👑C. 任务 ID 前缀 + Conventional 中文本项目最合适🏆
D. 子 agent 自由小项目❌ 不可追溯
教练推荐:C(混合版)

commit 模板:

[S0-18] feat(auth): 实现登录端点 + JWT 签发 - 添加 /api/auth/login 端点 - 实现 bcrypt 密码校验 - 返回 7 天有效期的 JWT token - 单测覆盖率 90% 契约: contracts/openapi/auth.yaml brief: master/briefs/S0-18-auth.md Co-Authored-By: backend-agent <agent@orchestrator.local>

4 个关键点:

1
任务 ID 前缀
[S0-18] 立即定位到主控任务
2
Conventional type
feat/fix/docs… CI 可解析
3
scope 模块
(auth) 一眼看出改哪
4
Co-Authored-By
标记 agent,出问题定位
🔀 Q3 · 合并节奏

子 agent 完工立即合主控?还是攒一批?

选项速度风险适用
A. 完一个合一个快中(频繁冲突)小团队
B. Sprint 末批量合慢高(大爆炸)❌ 不推荐
👑C. 长开 PR + CI 自动合中低AI 时代
D. 主控仲裁后合慢极低关键模块
教练推荐:A + C 混合 · 两档制
🟢 普通任务 → C(完工自动合)
子 agent 完工
  ↓ push feature/S0-18
触发 GitHub Actions
  ├─ contract-lint
  ├─ unit test
  ├─ build
  └─ 全过 → 自动 squash merge 到 main
🔴 敏感任务 → D(主控审才合)
  • 改了 contracts/ 的任务
  • 跨模块的任务
  • 数据库迁移任务
  • 影响主链的任务
判断标准: 看 feature_list.json 任务的 subproject 字段:

· contracts / master → 主控审

· backend / frontend / ai-orchestrator → CI 自动合

⚔️ Q4 · 冲突解决

两个 agent 改同一文件怎么办?

选项评价
A. 主控仲裁✅ 关键时刻必须有
B. 后到让先到❌ 不公平
👑C. CLAUDE.md 强制边界🏆 防患于未然
D. 三方合并工具✅ git 自带,兜底
教练推荐:C 优先 + A 兜底 + D 自动 · 3 层防御
第 1 层 · 边界约束(C · 99% 的情况)

在每个子项目 CLAUDE.md 里写死规矩:

  • backend-agent 只能改 backend/
  • frontend-agent 只能改 frontend/
  • 谁都不能改 contracts/(除非主控明确派任务)
  • 公共文件(README/CLAUDE.md)只能主控改
第 2 层 · 自动合并(D · 真冲突时)

git rebase + 自动 merge:

  • 不同文件 → git 自动合 ✅
  • 同文件不同行 → git 自动合 ✅
  • 同文件同行 → 进第 3 层 ⚠️
第 3 层 · 主控仲裁(A · 万分之一)

主控读两边代码,判谁对:

  • 在 progress.txt 记录裁决
  • 必要时开 ADR
  • 败方 agent 重新基于胜方代码做
🔒 Q5 · 契约保护(最关键!)

contracts/ 是禁区,要不要 hook 阻止?

选项评价
👑A. pre-commit hook🏆 必做
👑B. CI 检测🏆 必做(双保险)
C. 仅靠 CLAUDE.md❌ AI 偶尔会忘
D. 文件权限❌ Windows 不友好
教练推荐:A + B 双保险

🛡️ 第 1 道防线 · pre-commit hook(本地拦截)

# .git/hooks/pre-commit
#!/bin/bash

# 检查是否改了 contracts/
CHANGED=$(git diff --cached --name-only | grep "^contracts/")

if [ -n "$CHANGED" ]; then
  # 检查是不是主控 agent 在 commit
  if [ "$AGENT_TYPE" != "orchestrator" ]; then
    echo "❌ 拒绝 commit: 子 agent 不能改 contracts/"
    echo "改动的文件:"
    echo "$CHANGED"
    echo ""
    echo "如需修改契约, 请联系主控发起 ADR。"
    exit 1
  fi
fi

# 跑契约 lint
python scripts/contract-lint.py || exit 1

🛡️ 第 2 道防线 · GitHub Actions CI(远程兜底)

# .github/workflows/protect-contracts.yml
name: Protect Contracts
on: [pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 检查 contracts/ 改动
        run: |
          if git diff --name-only origin/main | grep "^contracts/"; then
            if [[ "${{ github.actor }}" != "orchestrator-bot" ]]; then
              echo "❌ 只有主控可以改 contracts/"
              exit 1
            fi
          fi
      - name: 跑 contract-lint
        run: python scripts/contract-lint.py
