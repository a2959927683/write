📖 背景

为啥需要 git 规则?

主控将派多个子 agent 并行干活:

  • 🎨 frontend-agent(Vue 3)
  • ⚙️ backend-agent(NestJS)
  • 🧙 ai-orchestrator-agent(Python)
  • 🗺️ knowledge-graph-agent
  • 🔧 infra-agent(Docker)

⚠️ 5 个 agent 同时改代码,如果没规则 = 必爆炸。

✅ 已达成共识

目前唯一定下的事

🎯 A1 · 用 git worktree 隔离工作目录

每个子 agent 在独立 worktree 干活,避免互改对方代码。

git worktree add ../wt-backend backend-dev
git worktree add ../wt-frontend frontend-dev
git worktree add ../wt-ai ai-dev
❓ 核心问题

5 个核心问题(全部待定)

Q1 · 分支策略

每个子 agent 用独立分支?还是独立 worktree?

A. 一 agent 一分支backend-dev, frontend-dev
B. 一任务一分支feature/S0-18-auth
C. 主线+worktree都基于 main,内部 commit
Q2 · commit 规范

commit 消息写什么风格?谁先 commit?

A. Conventional 英文feat(auth): implement login
B. Conventional 中文feat(auth): 实现登录端点
C. 任务 ID 前缀[S0-18] auth login endpoint
D. 子 agent 自由写清楚就行
🤔 关联问题: commit 是否要带 Co-Authored-By: Claude 或 agent 标识?
Q3 · 合并节奏

子 agent 完工立即合主控?还是攒一批合?

A. 完一个合一个简单,合并频繁
B. Sprint 末批量合中间互相看不到
C. 长开 PR + review走 PR 走流程
D. 主控仲裁后合主控审才能合
🤔 关联问题: 是否需要 CI 跑契约 lint?lint 不过禁止合?
Q4 · 冲突解决

两个 agent 改同一文件怎么办?

A. 主控仲裁自动 detect,主控判
B. 后到让先到时间戳优先
C. 强制隔离边界CLAUDE.md 写死
D. 三方合并工具git merge 自动
⚠️ 特别敏感: contracts/ 谁改谁错(除非主控显式批准)
Q5 · 契约保护

contracts/ 是禁区,要不要 pre-commit hook 阻止?

A. pre-commit hook改了直接拒 commit
B. CI 检测改了报警,主控决定
C. CLAUDE.md 约定仅靠 agent 自觉
D. 文件权限操作系统级只读
🔥 这是最关键的一题: contracts/ 一旦被乱改,所有 agent 都被带偏!

💼 备选方案

业界 4 套常见组合(供参考)

A · GitHub Flow 严格版

一 agent 一分支 + PR + CI lint + 主控批准合

✅ 流程严格,不易出错
❌ 流程重,多 agent 速度受限
B · Trunk-Based + Worktree

都基于 main,worktree 隔离,本地频繁 commit,定期 rebase

✅ 速度快,小团队友好
❌ 冲突频繁需自动化
C · 分形 (主控 main + 子项目 dev)

主控管 main,每子项目有 xxx-dev 长开分支

✅ 子项目自治,主线稳定
❌ 同步成本中等
D · 全混乱 (无规则)

子 agent 自由发挥,啥规则没有

❌ 必爆炸,不可接受!
