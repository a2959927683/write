💭 用户的想法

你的原始想法是什么?

每个子 agent 在自己的项目里操作,使用 harness 管理,5 阶段会生成"4 件套",feature 更颗粒化。

但你识别了一个关键卡点 ⚠️

🔥 卡点 · 研究阶段需要大量资料
  • 子 agent 启动就要读 knowlage/ 87 个 wiki 页 → Context 200K+ tokens
  • 读完发现 80% 不相关 → 浪费 token + 误导决策
  • 研究阶段花 30-60 分钟 → 还没动手
  • 多 agent 同时启动 → token 账单爆炸

✅ 教练判断:你的思路 = 一流团队的"分形 Agent 架构"。卡点也找得非常准。

💊 4 个解药

教练给你 4 个解药(组合用)

🥇
解药 1 · 预消化便当法
主控把"研究阶段"提前做完,给子 agent 一个便当盒。
必做
🥈
解药 2 · L3-v4-Lite
子 agent 砍掉"研究"阶段,只剩 4 阶段(规划/构建/复盘/调试)。
必做
🥉
解药 3 · 索引+检索
给 knowlage/ 写 INDEX.md,子 agent 按需检索不全读。
必做
🏅
解药 4 · 二级 Agent
把"研究"独立成短命子 agent,消化完就退场,释放 context。
按需
🍱 对比

便当盒 vs 菜市场 · 一图看懂

❌ 传统方式 · 让子 agent 自己去菜市场

子 agent ──► knowlage/ (87 页)
──► 自己消化
❌ 慢 / 贵 / 易出错

每个 agent 都要从头消化一遍 = 重复浪费

✅ 便当方式 · 主控提前消化好

主控 ──► 已消化好的 brief.md (5KB)
──► 子 agent 直接读
✅ 快 / 便宜 / 准确

主控写一次,所有 agent 受益 = 复用最大化

📦 便当长啥样

每个 brief 便当的标准结构

主控为每个任务产出 3 类内容,装在一个 markdown 文件里:

📋 master/briefs/S0-XX-xxx.md
🎯任务 · 5 行说清这个任务做啥
📜必读契约 · 精选 < 10KB(不让 agent 读全部)
🔧技术约束 · 明确边界(用什么不用什么)
✅验收命令 · 可直接执行的 curl/test
🚫不要做 · 反向约束,防止自由发挥
📚想深挖再看 · 链接列表,不强制读
📊 数字说话

预估效果对比

指标 原想法 (自己消化) 加 4 解药 (预消化)
子 agent 启动时间30-60 分钟2-5 分钟
Context 占用200K+ tokens15-30K tokens
Token 成本高降 80-90%
出错率中(自己消化易偏)低(主控已校准)
主控工作量低中(前期投入)

💡 主控前期投入 1 周写 brief,后期省下来的 token + 时间远超投入。
